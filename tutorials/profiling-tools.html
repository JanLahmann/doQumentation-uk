Інструменти для профілювання, налаштування та перевірки експериментів

Оцінка використання: 10 хвилин на процесорі Heron r2 (ПРИМІТКА: це лише оцінка. Твій час виконання може відрізнятися.)

Щоб отримати добрі результати від квантового комп'ютера, потрібна не лише добре спроєктована схема. На якість результатів впливають поточний стан пристрою, спосіб планування твоєї схеми, шум, який вона зазнає, а також те, коли і як твоє завдання виконується на квантовому процесорі (QPU). Qiskit та IBM Quantum® Compute Service пропонують дедалі більший набір інструментів розробника, що відкривають цю інформацію. Ти можеш використовувати ці інструменти, щоб діяти на основі цієї інформації до того, як витратиш час QPU на повний експеримент, і щоб налагоджувати завершений експеримент.

Цей навчальний посібник на одному наскрізному експерименті показує, як поєднувати ці інструменти на кожному етапі типового процесу розробки. Не кожен інструмент корисний для кожного експерименту, тож обирай ті, що відповідають на запитання щодо твого власного навантаження.

Робочий процес такий:

  1. Підготуй дзеркальну схему тротеризованої часової еволюції лінійної моделі Ізінга з поперечним полем.

  2. Обери бекенд з альтернативним набором калібрувальних даних, призначеним для методів пом'якшення помилок на основі моделі шуму.

  3. Запусти експерименти з бенчмаркінгу пристрою, щоб транспайлер використовував актуальні властивості пристрою під час вибору розкладки.

  4. Перевір інформацію про часові параметри запланованої схеми.

  5. Вивчи моделі шуму Паулі–Ліндблада та шуму зчитування для схеми.

  6. Виконай безшумні, непом'якшені та пом'якшені локальні симуляції. Шумні симуляції використовують вивчену модель шуму, щоб показати, наскільки покращення ти можеш отримати від вибраних методів пом'якшення помилок. Цей навчальний посібник використовує імовірнісне скасування помилок (PEC) і Twirled Readout Error eXtinction (TREX).

  7. Отримай оцінку використання без запуску на QPU, щоб перевірити, чи потрібно підлаштувати експеримент під твій бюджет.

  8. Запусти сесію та ініціюй калібрування, щоб експеримент використовував найновіші калібрувальні дані.

  9. Запусти експеримент на QPU за допомогою Estimator і порівняй апаратні результати із симульованим попереднім переглядом.

  10. Перевір проміжки виконання, щоб побачити, чи є значні прогалини між групами виконань (чанками).

Вимоги​

Перш ніж починати цей навчальний посібник, переконайся, що встановлено таке:

  • Qiskit SDK v2.3 або новіший із підтримкою visualization

  • qiskit-ibm-runtime v0.52.1 or later (pip install qiskit-ibm-runtime)

  • Qiskit Aer (pip install qiskit-aer)

  • Plotly (pip install plotly)

  • Qiskit Device Benchmarking (pip install git+https://github.com/qiskit-community/qiskit-device-benchmarking.git)

Вимоги до плану

Деякі кроки цього навчального посібника доступні не на кожному плані:

  • Завдання пробного запуску (кроки 2.4 і 3.5) доступні лише на планах Flex, Premium і On-Prem.

  • Сесії (крок 4.1) недоступні на плані Open. Щоб натомість запустити в режимі batch, встанови run_calibration = False на кроці 4.1.

Крок 1: Визнач схему та спостережувану​

Підготуй дзеркальну схему тротеризованої часової еволюції лінійної моделі Ізінга в поперечному полі. Віддзеркаль схему, щоб скасувати унітарну дію схеми та отримати тотожну схему. Оскільки ідеальний вихід — це стан з усіх нулів, ідеальне середнє значення кожної однокубітної спостережуваної ZZZ дорівнює 1. Віддзеркалення також подвоює глибину схеми, що посилює вплив шуму.

import numpy as np
from qiskit.circuit import QuantumCircuit
from qiskit.quantum_info import SparsePauliOp

def construct_ising_circuit(
    num_qubits: int,
    num_trotter_steps: int,
    rx_angle: float,
    barrier: bool = True,
) -> QuantumCircuit:
    circuit = QuantumCircuit(num_qubits)

    for _step in range(num_trotter_steps):
        circuit.rx(rx_angle, range(num_qubits))
        if barrier:
            circuit.barrier()
        for first_qubit in (1, 2):
            for idx in range(first_qubit, num_qubits, 2):
                # equivalent to Rzz(-pi/2):
                circuit.sdg([idx - 1, idx])
                circuit.cz(idx - 1, idx)
        if barrier:
            circuit.barrier()

    return circuit

def mirror_circuit(circuit: QuantumCircuit) -> QuantumCircuit:
    mirror_circ = circuit.copy_empty_like()
    mirror_circ.compose(circuit, inplace=True)
    mirror_circ.barrier()
    mirror_circ.compose(circuit.inverse(), inplace=True)
    mirror_circ.measure_active()
    return mirror_circ
num_qubits = 20
observables = [
    SparsePauliOp("I" * ((num_qubits - 1) - q) + "Z" + "I" * q)
    for q in range(num_qubits)
]

# Free parameters of the demonstration circuit: the number of Trotter steps
# sets the circuit depth, and rx_angle is the transverse-field rotation angle
# applied in each step (pi/4 makes the dynamics non-Clifford)
num_trotter_steps = 5
rx_angle = np.pi / 4

circuit = construct_ising_circuit(
    num_qubits, num_trotter_steps, rx_angle, barrier=False
)
mirrored_circuit = mirror_circuit(circuit)
mirrored_circuit.draw(
    "mpl", fold=-1, scale=0.3, idle_wires=False, measure_arrows=False
)

Крок 2: Оптимізація для виконання на квантовому обладнанні​

2.1 Використай альтернативне калібрування, якщо воно застосовне​

IBM® періодично калібрує свої QPU для хорошої продуктивності в загальних випадках використання. Проте деякі завдання виграють від інструкцій, параметри яких налаштовано інакше. Докладніше див. Спеціально калібровані інструкції.

У цьому підручнику використовується альтернативний набір даних калібрування під назвою slow_gates_ac. Це калібрування містить повільніший вентиль cz і модулює зміщення дворівневої системи (TLS), щоб стабілізувати помилки пристрою з часом. Ці зміни корисні для методів пом'якшення помилок, які спираються на вивчену модель шуму. Калібрування slow_gates_ac доступне лише на QPU Heron. Якщо ти працюєш на QPU Nighthawk, використовуй замість нього slow_gates.

from qiskit_ibm_runtime import QiskitRuntimeService

service = QiskitRuntimeService()
# Use slow_gates_ac because this tutorial uses a noise-learning-based mitigation method
backend = service.backend("ibm_kingston", calibration_id="slow_gates_ac")

2.2 Запусти бенчмаркінг пристрою в реальному часі​

Одним із найважливіших етапів транспіляції є вибір розташування, який відображає віртуальні кубіти схеми на фізичні кубіти цільового пристрою. Добре розташування мінімізує кількість потрібних операцій SWAP і розміщує схему на найпродуктивніших кубітах, тож якість початкового розташування може суттєво впливати на якість твоїх результатів.

На кожному QPU IBM періодично виконуються процедури бенчмаркінгу, які повідомляють поточну продуктивність його кубітів: часи релаксації (T1T_1T1​), часи когерентності (T2T_2T2​), помилки зчитування та помилки одно- й двокубітних вентилів. Транспайлер Qiskit використовує ці метрики під час вибору розташування.

Однак властивості надпровідних кубітів можуть дрейфувати на коротших часових масштабах, а тимчасові дефекти, відомі як TLS, можуть тимчасово погіршити кубіт, який добре працював під час калібрування. Якщо транспайлер використовує застарілу інформацію, він не може вибрати найкраще розташування. Тому може бути доцільно витратити трохи часу QPU на характеризацію пристрою перед вибором розташування.

Детальний покроковий розбір див. у підручнику Оновлення властивостей бекенда за допомогою бенчмаркінгу в реальному часі. Набір характеризації створює кілька експериментів, надсилає кілька завдань і підганяє результати. Весь цей процес може тривати кілька хвилин. Увімкни журналювання рівня INFO, щоб кожен етап виводив свій перебіг під час виконання.

import sys
import logging

logger = logging.getLogger("qiskit_device_benchmarking")
logger.setLevel(logging.INFO)
logger.addHandler(logging.StreamHandler(stream=sys.stdout))

BackendCharacterization — це зручний клас, який запускає обрані тобою експерименти характеризації, аналізує результати та повертає оновлений об'єкт Backend, який можна передати транспайлеру.

Ти можеш побачити попередження про те, що бекенд передано як режим, поки відкрито пакет. Це попередження очікуване, і його можна безпечно ігнорувати.

2.3 Транспілюй до ISA​

Перетвори схему та спостережувані відповідно до архітектури набору інструкцій (ISA) бекенда, використовуючи оновлені властивості пристрою.

isa_observables = [
    observable.apply_layout(isa_circuit.layout) for observable in observables

2.4 Візуалізуй часову діаграму схеми​

Окрім інструкцій у схемі, ти можеш захотіти візуалізувати розклад схеми, щоб знайти простій кубітів або неефективне вирівнювання інструкцій. Найдетальнішу та найточнішу інформацію про час можна отримати від IBM Quantum Compute Service за допомогою режиму dry-run.

Схема в цьому підручнику статична, тому її розклад не дуже інформативний. Подібну інформацію про час можна отримати локально зі схеми та властивостей бекенда, наприклад за допомогою timeline drawer, вбудованого в Qiskit. Цей підручник містить цей крок, щоб показати, як запитати та візуалізувати інформацію про час. Інформація про час від сервісу найкорисніша для динамічних схем. Динамічні схеми містять вимірювання посеред схеми, умовні операції та feedforward, які додають неявні операції, як-от розсилання результатів вимірювань і визначення гілок. Час цих операцій неможливо визначити лише зі схеми та властивостей бекенда.

Докладніше див. Візуалізація часу схеми. Час запланованої схеми доступний лише для завдань Sampler і Executor, тому наступна комірка надсилає схему в режимі dry-run за допомогою Sampler. Завдання, які ти надсилаєш у режимі dry-run, не виконуються на реальних QPU і не оплачуються.

from qiskit_ibm_runtime.executor_sampler import Sampler

sampler = Sampler(backend)
# Request timing information in the result metadata
sampler.options.experimental = {
    "execution": {
        "scheduler_timing": True,
    },
}

# Specify dry_run=True to submit in dry-run mode
sampler_job = sampler.run([isa_circuit], dry_run=True)
job_result = sampler_job.result()
circuit_schedule = job_result[0].metadata["compilation"]["scheduler_timing"]
circuit_schedule_timing = circuit_schedule["timing"]
from qiskit_ibm_runtime.visualization import draw_circuit_schedule_timing

# Create a figure from the metadata
fig = draw_circuit_schedule_timing(

Крок 3: Застосуй пом'якшення помилок і протестуй локально​

3.1 Кліффордизуй схему​

Вартість загального симулювання з шумом зростає експоненційно з кількістю кубітів, і більшість ноутбуків не можуть симулювати понад приблизно 32 кубіти. Тому спершу перетвори схему на схему Кліффорда, яку симулятор стабілізаторів може обробити значно ефективніше. Перетворення округлює кожен кут обертання до кута Кліффорда, тож симульована схема наближає вихідну, а не відтворює її точно.

3.2 Застосуй PEC з TREX​

Може бути складно вибрати методи пом'якшення помилок, які збалансовують вартість і точність для твого конкретного експерименту. Ти можеш використати навичку AI-агента select-error-mitigation, щоб проаналізувати доступні методи для твого завдання. Навичка подає зведений звіт, який пояснює, чи було обрано кожен метод і чому.

Додаткову інформацію див. у репозиторії GitHub Qiskit AI skills. Цей підручник використовує PEC з TREX безпосередньо, щоб ти міг пройти його без AI-агента.

PEC — це техніка, яка пом'якшує квантовий шум під час обчислення середніх значень спостережуваних. За ідеальних умов PEC може давати незміщену оцінку середніх значень. Вона вчить шум кожного шару двокубітних вентилів, а потім запускає ансамбль схем, які в середньому застосовують обернення цього шуму. PEC використовує Pauli twirling, щоб привести шум до каналу Паулі, який можна ефективно вивчити та інвертувати.

На практиці PEC настільки точна, наскільки точна вивчена модель шуму. Розріджена модель Pauli-Lindblad включає лише одно- та двокубітні доданки помилок на сусідніх кубітах і не може повністю охопити такі ефекти, як перехресні перешкоди між віддаленими кубітами або корельовані в часі помилки. Шум пристрою також може дрейфувати між навчанням шуму та виконанням. PEC не скасовує шум, який модель пропускає, і надмірно компенсує шум, який модель переоцінює. Тому пом'якшені результати все ще можуть відхилятися від ідеальних значень в обидва боки.

TREX — це техніка, яка пом'якшує помилки вимірювання і корисна, коли ти оцінюєш середні значення спостережуваних Паулі. Вона спирається на measurement twirling, який діагоналізує матрицю переходів помилок зчитування та спрощує її інверсію. TREX вчить масштабувальний доданок із діагонального каналу шуму, вимірюючи twirled калібрувальні схеми, ініціалізовані в нульовому стані. Ти можеш увімкнути і PEC, і TREX, налаштувавши параметри Estimator. Цей підручник використовує клієнтські реалізації інтерфейсів Qiskit SamplerV2 і EstimatorV2, представлені в qiskit-ibm-runtime v0.50.0. Ці клієнтські примітиви виконують більшість попередньої та післяобробки локально й делегують виконання примітиву Executor. Коли примітиви працюють на стороні клієнта, ти отримуєш більшу прозорість, швидший зворотний зв'язок під час налагодження та точніший контроль.

Клієнтські примітиви реалізують той самий API, що й застарілі серверні примітиви. Тому зазвичай можна перейти на клієнтські примітиви, змінивши лише інструкцію імпорту. Увімкни журналювання рівня INFO, щоб бачити перебіг клієнтської попередньої та післяобробки.

3.3 Вивчи моделі шуму та запусти кліффордизовану схему​

І PEC, і TREX потребують навчання шуму, яке можна виконати за допомогою NoiseLearnerV3. Кроки такі:

  1. Знайди унікальні шари двокубітних вентилів і шари вимірювань у схемі, відповідно для протоколів Pauli-Lindblad і TREX.

  2. Передай шари в NoiseLearnerV3, щоб вивчити моделі шуму.

  3. Перетвори вивчені моделі шуму на карти Pauli-Lindblad.

Estimator не використовує попередньо вивчену модель шуму TREX. Натомість він виконує власне навчання TREX. Наступний код усе одно вчить обидві моделі, оскільки симуляція з шумом використовує вивчену модель зчитування.

Докладніше про NoiseLearnerV3 див. Допоміжний засіб навчання шуму. Крім експерименту з навчання шуму, запусти кліффордизовану схему на QPU. Цей крок не завжди необхідний, але він надає порівняння для симульованих результатів у кроці 3.4.4. Запусти обидва в пакеті, щоб мінімізувати дрейф профілю шуму між ними.

3.4 Виконай локальну симуляцію​

За допомогою локального режиму qiskit-ibm-runtime ти можеш виконувати як безшумні, так і шумні симуляції локально з мінімальними змінами коду. Використовуй локальний режим, щоб перевірити синтаксичну коректність, порівняти вплив різних методів пом'якшення та перевірити, наскільки добре вивчена модель шуму узгоджується з результатами на обладнанні.

Локальний режим використовує значною мірою той самий інтерфейс, що й виконання на QPU. У більшості випадків потрібно змінити лише бекенд, який ти передаєш під час ініціалізації примітива, а потім повторно запустити той самий код. Кожен із наступних підрозділів створює власний екземпляр Estimator, тож їх можна запускати без зміни попередньої комірки.

3.4.4 Порівняй результати симуляції​

Побудуй графік середнього значення кожної однокубітної спостережуваної ZZZ із трьох симуляцій разом із непом'якшеним результатом QPU для тієї самої схеми Кліффорда з кроку 3.3. Оскільки схема є дзеркальною, кожне ідеальне значення дорівнює 1. Смуги похибок показують стандартну похибку, яку Estimator повідомляє для кожного значення.

Чим ближче непом'якшена симуляція до непом'якшеного результату QPU, тим краще вивчена модель шуму описує обладнання. Використовуй це порівняння як перевірку, перш ніж витрачати час QPU на пом'якшений експеримент. Якщо два результати значно розходяться, PEC також навряд чи наблизиться до ідеальних значень на обладнанні. У такому разі розглянь повторне навчання моделі шуму або вибір іншого розташування. Ти також можеш повторно вивчити модель шуму з іншими параметрами NoiseLearnerV3, як-от більше рандомізацій або додаткові глибини пар шарів, і перевірити, чи покращиться узгодженість. Наприклад, у кроці 3.3 цей підручник встановлює num_randomizations рівним 64 замість типового значення 32, оскільки додаткові рандомізації покращили узгодженість для цієї схеми.

NoiseLearnerV3 запускає стандартний протокол навчання. Для повного контролю над експериментом навчання ти можеш створити власний за допомогою Qiskit noise learning.

3.5 Оціни використання​

Основне призначення режиму dry-run — оцінка використання. На відміну від локального режиму, режим dry-run надсилає завдання до IBM Quantum Compute Service, який повертає точну оцінку використання, але випадкові дані результату. Завдання dry-run не виконуються на реальних QPU і не споживають жодного часу QPU.

Завдання dry-run недоступні на планах Open або Pay-As-You-Go.

Докладніше див. Завдання dry-run.

import time

dry_run_estimator = Estimator(mode=backend)
dry_run_estimator.options.resilience.measure_mitigation = True
dry_run_estimator.options.resilience.pec_mitigation = True
dry_run_estimator.options.resilience.layer_noise_model = zip(
    layers, pauli_lindblad_maps
)

dry_run_job = dry_run_estimator.run(
    [(isa_circuit, isa_observables)], dry_run=True

Крок 4: Запусти на обладнанні​

4.1 Ініціалізуй сесію та запусти калібрування​

Калібрування QPU оптимізує багато параметрів, що визначають електричні сигнали, які керують квантовими вентилями та операціями. Завдання калібрування виконуються протягом дня між завданнями користувачів, але не під час активної сесії. Ці параметри можуть дрейфувати за короткий проміжок часу. Для найкращих можливих результатів розглянь запуск калібрування на початку сесії або періодично під час тривалої сесії.

Наразі підтримується лише калібрування зчитування, і воно займає приблизно п'ять хвилин астрономічного часу.

from qiskit_ibm_runtime import Session, Batch, Calibrator

# Set to False to skip the session and calibration and run in batch mode instead
run_calibration = False
mode = Session(backend) if run_calibration else Batch(backend)

if run_calibration:
    calibrator = Calibrator(mode)
    # Wait for calibration to finish before submitting the experiment.
    calibrator.run().result()

4.2 Запусти на обладнанні з Estimator​

Наступні комірки запускають три завдання в пакеті або сесії:

  • Експеримент із навчання шуму для оновлення моделі шуму. Цей експеримент корисний, якщо ти очікуєш, що модель шуму з кроку 3.3 застаріє до моменту виконання завдання Estimator. Побудуй графік пом'якшених і непом'якшених результатів на обладнанні разом з ідеальними значеннями. Оскільки схема є дзеркальною, кожне ідеальне значення дорівнює 1, тож відстань між кожною точкою та пунктирною лінією показує залишкову похибку. Будь-яке залишкове відхилення від ідеального значення, вище чи нижче, відображає статистичну невизначеність PEC та обмеження вивченої моделі шуму, описані в кроці 3.2.

Щоб ще покращити результати, можеш спробувати таке:

  • Збільш кількість вимірювань (shots) або рандомізацій, щоб зменшити статистичну невизначеність пом'якшених оцінок. Вартість зростає разом із накладними витратами семплювання PEC.

  • Повторно вивчи модель шуму безпосередньо перед експериментом, у тій самій сесії, щоб зменшити вплив дрейфу шуму.

  • Вивчи модель шуму точніше, збільшивши параметри num_randomizations, shots_per_randomization або layer_pair_depths у NoiseLearnerV3. Помилки у вивчених швидкостях зміщують пом'якшені результати, а додаткові вимірювання PEC не усувають цього зміщення.

  • Додай перевірки немарковських помилок, щоб виявляти вимірювання, ймовірно спотворені немарковськими помилками, яких вивчена модель шуму не описує. Потім відкинь ці вимірювання постселекцією. Застосуй ті самі перевірки під час навчання моделі шуму, використовуючи параметри bit_flip_checks у NoiseLearnerV3. Інакше вивчена модель включатиме помилки, які постселекція видаляє з експерименту, і PEC надмірно компенсуватиме їх. Суворіша постселекція відкидає більше вимірювань, тож збалансуй приріст точності з кількістю вимірювань, які ти залишаєш.

4.3 Порівняй результати на обладнанні та в симуляції​

У кроці 3.4 ти використав локальну симуляцію, щоб попередньо оцінити, наскільки PEC і TREX можуть покращити результати. Порівняй цю оцінку з результатами QPU. Якщо покращення в симуляції та на обладнанні схожі, локальна симуляція є корисним способом оцінити налаштування пом'якшення для цього завдання, перш ніж витрачати на них час QPU.

Порівняння є наближеним з двох причин:

  • Симуляції запускають кліффордизовану схему з кроку 3.1, тоді як завдання на обладнанні запускають вихідну схему.

  • Симуляції використовують модель шуму, вивчену в кроці 3.3, тоді як пом'якшене завдання на обладнанні використовує модель шуму, оновлену в кроці 4.2.

Для безпосередньої перевірки самої моделі шуму використай порівняння результатів схеми Кліффорда в кроці 3.4.4.

4.4 Перевір проміжки виконання​

Коли ти надсилаєш схеми з кількома конфігураціями, наприклад із gate twirling, IBM Quantum Compute Service не обов'язково запускає всі конфігурації схеми одночасно. Натомість він групує їх у блоки й запускає один блок за цикл вимірювань. Цикл вимірювань — це один раунд виконання на квантовому обладнанні, під час якого кожна схема в блоці виконується задану кількість вимірювань.

Усі завдання, що надсилаються на реальний QPU, потребують певної класичної попередньої обробки, наприклад перетворення на імпульси, які можна надіслати на обладнання. Оскільки цю попередню обробку можна виконувати паралельно, сервіс виймає з черги та запускає кілька завдань одночасно. Проте QPU може обробляти лише одну одиницю роботи за раз. Тому, якщо твоє завдання генерує кілька блоків, вони можуть чергуватися з блоками завдань інших користувачів, і кожному блоку, можливо, доведеться чекати своєї черги на QPU.

Метадані результату завдання повідомляють час виконання на QPU для кожного блоку. Наступна візуалізація показує, чи є значні проміжки між виконаннями блоків твого завдання. Якщо проміжки ширші, ніж може витримати твій експеримент, можливо, варто повторно запустити завдання або використати режим виконання session, який надає твоєму завданню ексклюзивний доступ до QPU.

Рекомендації
  • Повторно запусти експеримент із калібруванням slow_gates_ac (крок 2.1), оновленими властивостями пристрою (крок 2.2) або калібруванням сесії (крок 4.1) і без них, щоб виміряти, наскільки кожен інструмент покращує результати для твого завдання.
  • Спробуй дешевший метод пом'якшення помилок, як-от екстраполяцію до нульового шуму (ZNE), і використай локальну симуляцію та оцінки використання dry-run, щоб порівняти його вартість і точність із PEC. Навичка AI-агента select-error-mitigation може допомогти зробити цей вибір.
  • Дослідж повний набір характеризації, включно з рандомізованим бенчмаркінгом, у підручнику Оновлення властивостей бекенда за допомогою бенчмаркінгу в реальному часі.
  • Дізнайся більше про клієнтські примітиви та Executor у Міграція із серверних на клієнтські Sampler і Estimator.
  • Застосуй ці інструменти до власних експериментів. Почни з інструментів, які усувають найбільше джерело невизначеності, як-от якість пристрою, шум, вартість або час виконання.
